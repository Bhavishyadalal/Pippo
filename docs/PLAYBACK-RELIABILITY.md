# Playback reliability and module URL fixes

Work branch: `preview-beta-v0.1.2`, starting at the restored `18d83a58` tree (same files as `1e17d0b8`). Main, stable and backup are preserved. The owner explicitly authorized logic/function testing for this task; no APK generation, GitHub Actions or deployment is authorized or performed.

## Findings and changes

- **False offline state during network handover.** The previous observer listened to all internet-capable networks and reported offline whenever any one disappeared. Availability was also reported before validation. It now observes the default network, uses validated capabilities, ignores late events from a replaced network, and exposes replaying StateFlow rather than splitting events between Channel consumers. Unregister is safe after a failed registration or a repeated cleanup.
- **Output failures mistaken for provider failures.** AudioTrack errors previously reached provider fallback and aggressive stream-cache eviction before the output-specific recovery branch. Output recovery now runs first, without discarding healthy streams. Repeated output failure stops with an output-specific explanation.
- **Recovery cancelling itself before resume.** READY cancels pending retry jobs. The old AudioTrack recovery waited after preparing before restoring playback, allowing READY to cancel the only resume step; cancellation was then caught as another failure. Play intent is restored before prepare, cancellation propagates normally, and explicit pause requests invalidate delayed recovery even if the player was already paused internally.
- **Stale delayed retries.** Recoveries are tied to the failed song and player, with media-item transitions cancelling old work and clearing old network-wait state. Network-triggered retries count toward the retry budget too. Invalid HTTP content types use bounded I/O/provider recovery rather than being labelled as lack of internet.
- **Bluetooth routing.** A one-shot settled-device notification accounts for Android announcing hardware before its media route settles. A changed Bluetooth route can flush the current local AudioTrack via a same-position seek after a short settle delay. It does not force play, unmute, override an explicitly selected output, run during a crossfade, or restart local playback while casting. LE Audio devices join A2DP in the optional Bluetooth auto-resume behavior; SCO call-only endpoints do not trigger music auto-resume.
- **Exclusive DAC routing.** Route changes now invalidate the exclusive-output decision, and its eligibility follows the selected active output instead of merely finding a connected DAC. A retiring output that stops advancing cannot block handover indefinitely; draining has a three-second bound.
- **Copy module URL.** Module details show the resolved URL and an existing-style copy pill in the Info card. Prefer saved installation source, then web origin, then known servers (including built-in Monochrome), then a module-provided source/sign-in landing URL. Only HTTP(S) links with a host are offered; local/invalid links are omitted. YouTube Music and JioSaavn are excluded. Copying uses the local clipboard, without a network request or account-token lookup. Android 13+ supplies its normal clipboard confirmation; earlier versions receive a short toast.
- **Crossmix duration regression found by the full suite.** Overlap limits now use the actual exit-grid period and final successful match, rather than approving a longer matched overlap before beat fitting could fail. The no-candidate fallback also respects the unmatched-duration limit and listener length setting instead of always using sixteen beats.
- **Missing language choices found by the full suite.** The picker includes all translated regional resources, using canonical BCP-47 tags. The resource consistency test still demands exact coverage and additionally verifies canonical picker tags, including legacy Hebrew regional aliases.

## Verification

The focused network, route/recovery, module-link and cache-key tests passed (14 tests). The subsequent full app unit run found two additional failures in crossmix duration and language-resource coverage; the corrections above address both. After correcting both failures, the final full app run passed **197 tests, 0 failures, 0 errors, 0 skipped** (`:app:testArm64GmsDebugUnitTest`). The existing crossmix fallback test now also checks its minimum and maximum duration; the language test retains exact resource coverage and checks canonical tags.

Tests compile application code for the ARM64 GMS debug unit-test variant. No APK is assembled. These JVM tests cover routing/recovery decisions, network handover sequences, URL precedence/validation/exclusions, and the existing application tests; they do not reproduce an OEM Bluetooth stack or audible output.

Physical TWS reconnection, Android output selection, background playback, audio focus/call interruptions, casting, and real slow/flaky networks still need device testing. A route flush may cause a brief handover interruption. No claim that the entire app is bug-free or that the reported hardware symptom has been reproduced is made.
